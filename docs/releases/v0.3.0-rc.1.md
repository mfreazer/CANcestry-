# CANcestry v0.3.0-rc.1 — release notes

**Status: draft for the `v0.3.0-rc.1` release candidate.** This file is the
in-repo copy of the announcement; it is written to be published as the body of
the GitHub Release (and quoted on the project's channels) once the release-prep
PR is merged and the tag is cut. Everything below is reproducible from the
tagged commit.

> **Describe the bus, teach the machine, emulate the module.**
> v0.3.0-rc.1 is the first CANcestry release where all four portable cores run
> together in one deterministic, zero-heap gateway loop: raw CAN frames in,
> decoded signals, recipe and state-machine behaviour, encoded frames out — with
> no heap allocation and byte-identical output on every run.

## Headline

- **Deterministic event model** — one event structure, one bounded queue, one
  selection order (timestamp → priority class → sequence) and one overflow
  policy, shared by every layer.
- **opendbc parity** — third-party DBC files convert to CANcestry codec maps with
  provenance headers and decode bit-identically to comma.ai's `opendbc` parser.
- **Recipe engine** — declarative, event-triggered, condition-gated
  transformations between the event bus and the codec engine, with a fail-closed
  governor checkpoint.
- **FSM runtime** — allocation-free, deterministic state machines with guards,
  expressions, timers, capability enforcement, bounded work and golden-output
  tracing, verified by a seven-suite conformance harness.
- **They run together** — `examples/gateway/main.c` wires the four cores into one
  ingress → decode → queue → recipe/FSM → encode → egress loop and asserts, in a
  single program, the properties this release is about.

## Why "deterministic" is a claim you can check

The project does not ask you to take determinism on faith:

- **Same input, same bytes.** The gateway harness builds the world twice from the
  same definitions and runs it independently; the full output log and every
  egress frame must compare byte-identical (`SYS-NF-001`, `SYS-FR-014`,
  `SW-FR-FSM-046`). Time comes only from an injected virtual clock — no wall
  clock, no `rand`, no hash iteration anywhere in the path.
- **Zero heap, proven twice.** A runtime allocator tripwire (glibc hosts) counts
  allocation calls across the whole processing loop and reports zero; in parallel,
  `ci/check_no_alloc.py` scans the core archives and the harness object for
  allocator references, which also covers the AddressSanitizer configuration
  where the tripwire is unavailable (`SYS-NF-002`).
- **Fail closed.** A governor denial and an expression fault are recorded, the
  offending FSM instance is suspended, and the loop keeps draining its queue
  (`SW-FR-FSM-024/038`, `SW-FR-GOV-005/006`, `SYS-SF-002`).
- **The whole record is audited.** 149 requirement ids are defined across the
  SyRS and SwRS; 107 are traced to verification artifacts (124 passing rows, 22
  planned, 0 failed) and the 55 deliberately deferred ones are listed with the
  phase that owns them. `ci/check_traceability.py` fails the build if a passing
  row stops resolving to a real test or a requirement quietly disappears.

The executed evidence — commands, exit statuses, the golden-output hash and the
(on-host) zero-allocation result — is in the
[v0.3.0-rc.1 smoke test record](../qa/smoke-test-v0.3.0-rc.1.md).

## Try it in a minute

```sh
git clone https://github.com/mfreazer/CANcestry-.git && cd CANcestry-
git checkout v0.3.0-rc.1                 # once the tag exists
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug   # Debug enables ASan + UBSan
cmake --build build --parallel
ctest --test-dir build --output-on-failure     # 31 tests, including the gateway
./build/examples/gateway/cancestry_gateway     # prints the golden loop output
python3 ci/check_traceability.py .             # audits the coverage claims
```

The harness is self-contained: it needs no hardware, no CAN interface and no
network — definitions are embedded, ingress is a fixed frame sequence and egress
is a recording sink.

## What is *not* in this release candidate

Stated plainly, because "release candidate" should not mean "everything":

- **No physical CAN, no bus behaviour.** The CAN integration and platform layer
  (`SW-FR-CAN-001..006`, named interfaces, bus-off recovery) is a later phase.
  The harness is a logic harness; real-world bus validation is not claimed yet.
- **No package loader.** v0.3.0-rc.1 loads individual codec maps, recipes and FSM
  files; the package manifest, integrity hashes and version-compatibility rules
  (`SW-FR-PKG-001..007`, `SYS-SEC-001`) come with the package layer.
- **No logger/replay and no host simulator** (`SW-FR-LOG-*`, `SW-FR-SIM-*`,
  `SYS-FR-011/012/013/020`).
- **Governor at stub level.** Fail-closed denials are enforced and tested
  (`SW-FR-GOV-005/006`); token buckets, ID-level rate limits and SAFE mode
  (`SW-FR-GOV-001..004`, `SYS-SF-001/003/004`) are still to come.

The full list, with the owning phase for each entry, is the deferred ledger in
[`docs/trace/traceability.md`](../trace/traceability.md) section 5 — and the CI
gate keeps it honest.

## Upgrade notes (0.2.0 → 0.3.0-rc.1)

- `VERSION` and `CMakeLists.txt` report `0.3.0`. `schemas/fsm-0.3.0.schema.json`
  is the FSM target; it is the 0.2.0 structure unchanged, and loaders still accept
  `"0.2.0"` documents.
- Fields outside the schema — including `layout` (a codec-map field) and
  `priority` (a runtime event class) — are rejected at load time rather than
  ignored, in every loader with `additionalProperties: false`.
- The gateway example is a host build, controlled by `CANCESTRY_BUILD_EXAMPLES`
  (default `ON`, skipped when cross-compiling). It compiles with `-Wconversion`
  on top of the project warning set.
- Loading a declarative file may allocate once; nothing on the runtime path does,
  and CI enforces both sides.

## Community: what feedback would help most

This is a release candidate, and the questions below are open on purpose (they
are recorded in [`core/fsm/README.md`](../../core/fsm/README.md) rather than
silently decided). Comments in the tracking issue or new issues are welcome:

1. **Fault reaction policy** — should an expression fault suspend the instance
   (current) or skip the action and raise a package fault?
2. **Queue semantics on fault-on-fault saturation** — `docs/system/event-ordering.md`
   section 11.2 and the shipped `core/event` primitive disagree; which should
   win?
3. **Internal transitions** — does the FSM schema need an `internal` flag for
   `state_entered`/`state_exited`?
4. **Real-bus profiles** — if you have captures or DBCs from a vehicle or bench
   you care about, the parity harness is the fastest place to see whether the
   codec engine handles them.
